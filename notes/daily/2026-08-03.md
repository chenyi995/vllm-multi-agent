### 2.1 本 commit 与计划成文时不同的 API（都会静默出错）

1. **`apply_chat_template` 在 transformers 5.x 返回 `BatchEncoding` 而非 list**。
   计划 §3「铁律」那段代码直接用会把字符串当 token 传进去。正确写法是取 `enc["input_ids"]`。
   **这条如果没抓到，token 位置全错，de-RoPE 整个作废。**
2. **`llm.generate(prompt_token_ids=[ids])` 旧 API 已删除**，改成
   `generate(TokensPrompt(prompt_token_ids=ids), ...)`。
3. **模型 `generation_config.json` 带 `temperature=0.7 / top_k=20 / top_p=0.8`**，vLLM 默认会合并进来，
   污染计划要求的 `temperature=0` 口径。已设 `generation_config="vllm"` 不加载模型默认值。
4. **flashinfer 采样器**是 cu13 版且首次采样会 JIT 编译（集群 PATH 里没有 ninja 会直接崩）。
   贪心解码用不上，已设 `VLLM_USE_FLASHINFER_SAMPLER=0`。
5. **必须显式设 `max_model_len`**：模型是 262144 上下文，vLLM 要求 KV 池装得下一条满长请求，
   否则引擎起不来。当前取 **65536**（高于任何单次调用，低于 A5000 的 93,424 token 池）。
   ⚠️ 受限档有耦合：设了 `num_gpu_blocks_override` 后**准入检查按压低后的池子算**，
   所以受限档的 `max_model_len` 必须 ≤ 0.5×W。

### 2.2 探针实测的引擎内部事实

- 对象图：`llm.llm_engine.engine_core.engine_core.model_executor.driver_worker.worker.model_runner`
- KV 张量：36 层，单层 `(num_blocks, 8, 16, 256)` bf16，stride `(32768, 256, 2048, 1)`（非 contiguous）
- **K/V 打包顺序**（`flash_attn.py:1114` 的权威依据）：
  `kv_cache.transpose(1,2).split(head_size, dim=-1)` → **K 是前 128 维，V 是后 128 维**
- 后端 FlashAttention（非 FlashInfer）；A5000 上 `num_gpu_blocks=5839` = 93,424 token
- `BlockHashToBlockMap` **不可遍历**（只有 contain/get_one_block/insert/pop），
  dump 取 block_id 必须扫 `pool.blocks`
- `block_hash` 在本 build 里是 **int**（`VLLM_KV_EVENTS_USE_INT_BLOCK_HASHES` 默认开）
- **`BlockStored` 只代表新增缓存的 block**：复用事件只在 `kv_cache_report_mode == "full"` 时才发，
  默认 `"incremental"`。改这个默认值会让 N_total 静默高估。
- 事件按 `hash_block_size`（= `prefix_match_unit`）粒度发，4/8 档能直接从事件流拿到 4/8-token 单元

### 3.1 sanity #1

原判据「max abs err < 1e-2」**实测不通过，且该判据本身不可达**：

```
                        max abs err   max abs/max|k|   cosine(k_rec, k_pre)
cos/sin 走 bf16(=vLLM)    1.34e-01       4.3e-04        0.9999999692
cos/sin 走 fp32           9.52e-02       3.0e-04        0.9999999805
                                         逐 token 最小 cosine = 0.9999999254
```

原因：K 有 attention-sink 式离群值，实测 `|k_post|` 最大 **314** 而均值仅 2.35，
BF16 存储下 1e-2 的绝对阈值物理上到不了。佐证：用本仓库 `rope()` 正变换去对 vLLM 自己的
`k_post`，误差同为 6.2e-2 量级——1e-2 比 vLLM 自身数值噪声还低。
宸逸拍板改成 cosine 判据。

### 3.2 dump 通路（顺带验证，不在原清单）

```
缓存里的 K  vs  钩子抓到的 post-RoPE K：74 个 token 全比，max abs diff = 0.000e+00
```
一次性验证了张量布局、K/V 打包顺序、block→position 映射。block_size=16 与
block_tier=4（`prefix_match_unit=4`）两档都过。

期间修掉一个真 bug：`prefix_match_unit` 比物理 block 细时，hash 覆盖的结束位置会落在 block 内部，
原先用 `end - block_size` 反推起点会让 4/8 两档 position 整体错位——**de-RoPE 会全错且不报错**。
改成按 block 边界取起点。

### 3.3 sanity #4

第一次报 7 处不一致，查下来**是对账工具自己的 bug**：`RadixTree` 没处理
`AllBlocksCleared` 和 `BlockRemoved`，reset 之后仍把上个 workflow 的块算作可命中。
修完 38 次调用里 37 次精确一致、1 次在允许的一块误差内。

副产品：那 7 处「误判命中」的 128 token 正是**跨 workflow 的同内容前缀**，
说明跨 workflow 重复信号真实存在。

**当天晚些时候又抓到同一工具的第三个 bug**：T7 报 26/35 不一致，规律是每个 workflow 的
第 0 次调用都预测 32 token 命中而引擎报 0。根因是 `reset_prefix_cache()` 发出的
`AllBlocksCleared` **由引擎发布线程异步打时间戳**，可能晚于 driver 记录的 `t_start`，
按时间过滤就清不干净。改成**按事件流里的 `AllBlocksCleared` 分段**、每个 workflow 只看
自己那一段之后，**全部 14 组 100% 精确一致通过**。

> 三个 bug 都在对账工具里，数据本身没问题。这也说明 sanity #4 值得反复跑——
> 它抓的是分析侧的错，而分析侧的错同样不会报错。

### 3.4 sanity #6 —— 当天最重要的发现

**噪声不来自「重算」本身，来自「重算时 prefill 形状不同」。**

| 重算条件 | 结果 |
|---|---|
| A 完全驱逐 + 整条重新 prefill | 1050 对中 930 对**逐位相同**，cosine 精确 1.0 |
| B 部分前缀命中、只重算后缀 | 1050 对中仅 144 对逐位相同 |

条件 A 逐位复现，是因为重算时 batch 形状与首次完全相同 → GPU 归约顺序相同 → 浮点结果一致。
前缀缓存的常态是部分命中（后缀以更短的 batch 重新 prefill，归约顺序改变），故 τ 只能取自条件 B。
**按条件 A 标定会得出「噪声为零、τ = 1.0」的假结论**——第一次跑就是这样。

条件 B 的分布：

```
           min          P1           P50
K_post     0.94385      0.98054      0.99968
K_derope   0.94385      0.98054      0.99968
V          0.88306      0.96098      0.99802
```

逐层（噪声逐层累积，第 N 层输入是第 N−1 层带误差的输出）：

```
layer  0:  P1 = 0.99999
layer  8:  P1 = 0.99998
layer 17:  P1 = 0.97809
layer 26:  P1 = 0.96400   ← 最大噪声点
layer 35:  P1 = 0.99648   ← 回落，原因未查
```

跨度近三个数量级，宸逸拍板 **τ 逐层标定**。
另：V 的重算噪声比 K 更大，「V 是干净对照」只对**位置无关性**成立，对**数值稳定性**不成立。

当前 τ 取自单条 prompt × 7 个命中边界（1050 对），是工作值，正式跑批后须在真实 trace 上重标。
数值落盘 `traces-sanity6/SANITY6_b16_limited/tau.json`。

## 5. 实测的量

```
单 workflow 工作集 W    80,480 / 90,192 / 135,088 token   ← 随题目波动很大，不是常数
单 workflow dump 体积   1.6 GB（5 个采样层）
单次调用长度            layer 0 prompt 50 token → aggregator prompt 6,801 token
单 workflow 耗时        A5000 上 7.2–9.4 分钟（19 次调用）
单组配置耗时            约 90 分钟（10 题）  ← athena 方案 §5.3 估的是 40 分钟
```

由此确认：**充足档只能跑 L40S**。A5000 的 9.3 万池装不下 13.5 万的 workflow——
实测在 node4 上驱逐了 2,606 个 block，`ample_criterion_met=false`。

## 7. 第二波：容量口径重定、九个 driver 写完、首批计数

### 7.1 为什么把两个容量档收到同一种卡上

原分工是「充足档 L40S / 受限档 A5000」。问题在于 **Q3 的 join 横跨两种 GPU 架构**：
受限档拿驱逐名单去 join 充足档算出的重复判定，而 sanity #6 的保真度只在**同一张 A5000
内部**测过，跨卡（Ampere sm_86 ↔ Ada sm_89，FlashAttention 的 tile 划分可能不同 →
归约顺序不同）**从未测量**。

宸逸拍板：`max_tokens` 从 MoA 原文的 2048 压到 **1024**（原值几乎不生效但会让单 workflow
涨到 13.5 万 token），`gpu_memory_utilization` 从 0.90 提到 **0.95**（池子 93,424 → 102,048）。
两档都跑 A5000，跨卡变量消失。次要收益：L40S 长期零可用，A5000 有 5 张空闲。

⚠️ 记录混淆：压短输出让固定长度的 persona/提示词占比上升，**可能人为抬高重复率**。

### 7.2 容量规则的两次修正（都是实测逼出来的）

**第一次：max → mean。** T1 各 workflow 工作集
`[8176, 3872, 7232, 7760, 7696, 23520, 8416, 6624, 5776, 6352]`，第 6 个是离群值。
按 `0.5 × max` 得池子 11,760，**比其余 9 个 workflow 各自的整个工作集还大**：

| 规则 | 池子 | 真正受限的 workflow |
|---|---|---|
| `0.5 × max(W)` | 11,760 | 1 / 10 |
| **`0.5 × mean(W)`（采用）** | 4,271 | 9 / 10 |

**第二次：加下限。** T2 的 `0.5 × mean = 1,024`，而它最长的单次调用是 **2,922** token——
池子装不下一个请求，vLLM 会直接拒绝。改成
`max(0.5 × mean(W), 1.1 × 最长单次调用)`，并在 manifest 里如实记录
`capacity_floor_applied` 与 `achieved_ratio_vs_mean`。

> KVFlow 的 0.5 口径假设工作集是 8 万 token 量级（10 agent × 8192），
> 而 T2/T7 的工作流只有 2–3k token，一半装不下一个请求。**对短工作流该比例物理上不可达**，
> 这一点本身就是结论的一部分，不能掩盖。

实例：T1 `W_mean=8,715`、最长调用 4,683 → 下限 5,152 生效 → 实际比例 **0.59**。

  覆盖 T1（MetaGPT 五角色）、T3（MoA 七用例）、T8（CAMEL 两段）、T9（ToT 两段）。

### 7.4 首批重复度计数（C6）

`kvpim.analyze.count_duplicates` + `build_counts_table` → `traces/counts.parquet`。
先按元数据分组，只有 ≥2 成员的组才加载张量，**一组配置约 6 秒**。

T1 b16 充足档：

```
n_total            = 5,459 个 block
n_blocks_in_groups = 2,872（52.6%）有内容孪生   ← 理论天花板
分组: 两两 808 组 / 三个 224 组 / … / 十个 19 组
来源: 同题内 2,627（91.5%）、跨题 245（8.5%）
```

逐层三视角（单位：块）：

| 视角 | L0 | L8 | L17 | L26 | L35 | 全层 |
|---|---|---|---|---|---|---|
| `K_post` | 202 | 200 | 200 | 200 | 200 | 200 |
| `K_derope` | **2,872** | 200 | 371 | 526 | 405 | 200 |
| `V` | **2,872** | 167 | 254 | 314 | 222 | 167 |

> **首个实质结论：位置不是唯一的障碍，上下文才是。**
> 第 0 层 de-RoPE 把可去重量从 202 抬到 2,872（**14 倍**），因为那一层的 K 只取决于
> 「哪个词 + 第几位」；到第 8 层收益归零，因为深层的 K 取决于**前面的上下文**，
> 同内容不同前缀的块在深层是**真的不同**，逆旋转救不回来。
> 对 KV-PIM 的含义：位置无关存储的收益**集中在浅层**。

单调性检查通过：每一层、每一组 `K_derope ≥ K_post`。

⚠️ **5 层采样是上界**：真要去重两个 block，**36 层全都得相同**（一个物理 block 装全部 36 层）。
我们只查 5 层，可能放过在未采样层其实不同的块对。所以「5 层全判同」是「36 层全判同」的
**上界**，真实值只会更小。宸逸决定**不做 36 层对照实验**，该偏差如实记录在
`notes/workloads/README.md` §10。

### 7.5 调度：我们把整个节点堵住了

实测每个作业**只用约 1 个核**（6 个作业合计 597% CPU），而我们按 athena 方案申请
`-c 16`——6 个作业 × 16 核 = 96 核，**吃光 node1 全部 CPU**，导致那 2 张空闲 GPU
连别人都拿不到。宸逸拍板新作业改 `-c 4`，并把我们的卡量上限定为 **10 张**。

`T4充足→T4受限→T5充足→…` 六组，中途不放卡，避免 90 次「释放再抢」。
