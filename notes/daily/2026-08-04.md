## 2. 两次静默卡死（当天最大的教训）

### 2.1 三个作业被 15 小时时限杀掉，白烧 45 卡时

`G789-b4/b8/b16` 停在 6 组里的第 2 组，日志显示 `CANCELLED DUE TO TIME LIMIT`。
查明：

```
T7 b4 受限档池子 = 1,392 token   （0.5 × mean(W)，这三个作业启动早于"容量下限"补丁）
T7 最长单次调用 = 2,169 token
→ 请求永远等不到足够的 block，不报错、不崩溃，静默挂死
→ 跑完 4 次调用后卡住，直到 15 小时时限
```

### 2.2 `T1-b32-limited` 也卡死，而且它**已经有下限保护**

```
充足档同一批题最长调用   4,681 token
受限档实际跑出的最长     5,008 token   ← 超过了充足档的最大值
池子（按 1.1 × 4,681）   5,152 token   ← 撞上去了
```

**根因是新的**：受限档发生驱逐 → 重算的浮点噪声（正是 sanity #6 量的那个）
**翻转了 greedy 的选词** → 对话内容分叉 → 后续 prompt 长过充足档的最大值。

> **所以"下限按充足档最长调用取值"不安全——受限档的最长调用不受充足档约束。**

### 2.3 修法

1. 容量下限 `1.1 × 最长调用` → **`1.5 ×`**
2. **看门狗**：`run_group.sbatch` 与 `run_config.sbatch` 都加
   `timeout ${CONFIG_TIMEOUT:-3600}`，单组超 1 小时就杀掉并继续下一组
   （实测最重的 T8 也只要 28 分钟）

**教训**：容量不足在 vLLM 里表现为**静默挂起**，不是报错。没有看门狗，
一次配置失误就能吃掉整个分配。

## 3. sanity #4 又修了两次，最后拆成两种模式

（前三次修正记在 08-03 的记录里。）

**第四次**：7 组 T4 失配，`gap` 恰好 16。引擎永远留**最后一个物理块**重算，
而我按 `prefix_match_unit`（4/8 档是 4）写容差，太小。改成物理 `block_size`。

**第五次不是修，是缩范围**：5 组 `T4_*_limited` 仍失配，且 `gap` 是**负的**
（引擎报 3,328、我预测 96）。查明：

```
T4_w03 这一段：601 个块存过，325 个被驱逐
```

**在一个 workflow 内驱逐 325 次、事件又由发布线程异步打时间戳的情况下，
"重建某一瞬间的精确缓存状态"这件事做不到。**

决定性检验——忽略驱逐、只问"引擎报的命中能不能被本 workflow 存过的块解释"：
**五个档、每一次调用全部通过。事件流是完整的。**

所以按容量档拆成两种模式，各自只声称数据能支撑的东西：

| 容量档 | 模式 | 判据 | 为什么 |
|---|---|---|---|
| ample | `exact-replay` | `predicted == reported`（容忍一个物理块）| 无驱逐，瞬时状态可精确重放 |
| limited | `completeness-only` | `predicted >= reported`（忽略驱逐）| 瞬时状态不可重建，但**完整性**仍可验，而这正是 sanity #4 的目的 |

**90 组全部通过。**

**防"调到变绿"的反向测试**（两种模式都做）：

```
充足/exact-replay     故意丢 529 个事件 → passed=False，3 处失配
受限/completeness     故意丢  69 个事件 → passed=False，10 处失配
```

## 4. 首批完整结果

### 4.1 Q1：去掉位置编码能多找回多少

第 0 层 `K_post → K_derope` 的增益倍数（block 档 16）：

```
T1 14.2×   T8 6.2×   T5 5.9×   T6 2.6×   T2 1.7×   T7 1.4×   T3 1.2×   T4 1.1×   T9 1.0×
```

**三条结论**：

1. **第 0 层 de-RoPE 把候选全部解锁——九类无一例外**（那一层的 K 只取决于
   "哪个词 + 第几位"）
2. **增益大小完全由"内容是否恰好落在同一位置"决定**：T1 的函数签名在五个角色的
   输入里位置各异 → 14.2×；T9 的 prompt 是同一模板只换数字、位置天然对齐 → 1.0×
3. **越深增益越小，5 层全判同时基本归零**

> ## 位置不是唯一的障碍，上下文才是。
> 深层的 K 是"看过前面所有 token"之后的产物。两段文字即使一字不差，
> 只要前面的上下文不同，深层的 K 就是真的不同——逆旋转救不回来。
> 对 KV-PIM：位置无关存储的收益**集中在浅层**。

### 4.2 Q2：block 大小的影响

内容孪生占比（理论天花板）随 block 增大**单调下降**：

```
T1: 52.6% → 26.4% → 11.6%     (b16 → b32 → b64，降 4.5 倍)
T2:  5.8% →  3.7% →  0.0%
T3: 72.7% → 65.4% → 62.9%     ← 唯一的例外，只降 13%
```

T3 的例外是因为它重复的是**几千 token 的整份 reference**，不是零星几个块，
放大 block 也切不断。

### 4.3 容量受限的代价：延迟不变，重算翻倍

| 拓扑 | 端到端延迟（受限/充足） | 需计算的 token（充足）| （受限）| 驱逐导致的多算 |
|---|---|---|---|---|
| **T5** | 1.03× | 17.9% | 36.7% | **+105.9%** |
| T6 | 1.00× | 23.8% | 31.3% | +31.1% |
| T1 | 0.99× | 49.4% | 56.9% | +14.9% |
| T4 | 0.96× | 37.1% | 37.9% | +2.1% |
| T2 | 0.98× | 47.5% | 47.5% | +0.0% |
| T3 | 0.99× | 98.7% | 98.7% | +0.0% |

**端到端几乎不变**（0.96–1.03×），因为解码占主导——两档都是每 token 约 **24 ms**，
驱逐的代价在 prefill，被解码淹没。

**规律：越依赖前缀缓存的拓扑，被驱逐伤得越重。** T5 充足档命中 82.1%，
受限档掉一半、重算翻倍；T3 本来只有 1.3% 命中，驱逐什么都拿不走。

## 5. 三个必须记下来的数据口径问题

### 5.1 ⚠️ 受限档的 KVFlow 0.5 比例，只有 T3 达成

```
45 个受限档里，40 个触发了容量下限
实际比例范围 0.591 – 2.181
其中 24 组的池子 > 平均工作集（比例 > 1.0），"受限"名存实亡
```

最极端的几组：

| 组 | 实际比例 | 池子 | W_mean | 最长单次调用 |
|---|---|---|---|---|
| `T4_b64_limited` | **2.181** | 4,800 | 2,201 | 4,332 |
| `T8_b16_limited` | **2.000** | 33,280 | 16,644 | 22,177 |
| `T2_b16_limited` | 1.564 | 3,216 | 2,056 | 2,922 |
| `T3_b16_limited` | **0.500** | 39,104 | 78,208 | 7,479 |

**根因是两个量不可比**：下限用的是 `1.5 × 最长单次调用`，而目标用的是
`0.5 × mean(W)`。**最长调用是"一个请求多长"，W 是"存了多少个不同的 token"**。
对内部复用重的 workload（T4 三个 agent 看同一个问题），**一个请求可以比整个
workflow 的去重工作集还长**。

**好消息**：45 组受限档**全部发生了驱逐**（无一为 0），sanity #3 满足，
因为 W 在 workflow 之间波动大，最大的那几个仍然撑破池子。

**影响**：**Q3 的前提"容量 = 工作集的 50%"实际只在 T3 上成立。**
其余八类是"容量 = 能装下最长请求的最小值"，各组的受限强度差异很大，
**跨拓扑比较 Q3 时不能直接并列**。各组 manifest 里
`capacity_floor_applied` 与 `achieved_ratio_vs_mean` 如实记着。

### 5.2 ⚠️ T3 的充足档判据没通过

九类里只有 T3 这样，五个档都是：

```
池子     = 102,048 token   (gpu_memory_utilization=0.95)
W_max    = 103,488 token   ← 第 3 个 workflow
驱逐     = 92 块 = N_total 的 0.19%
```

这正是把 `max_tokens` 定成 1024 时标出的风险：当时预估余量约 10%，
T3 实测把它吃穿了 1.4%。

**影响很小**：dumper 按 workflow 内的 block_hash 去重，重算存回不会重复计数；
受影响的只有那**一个** workflow 的事件层面指标。
宸逸决定接受并如实标注，不为 0.19% 牺牲跨拓扑的参数一致性。

### 5.3 ⚠️ 5 层采样是上界

真要在硬件上去重两个 block，**36 层必须全都相同**——一次分配横跨全部 36 层
（`block_id=5` 指每层张量的第 5 个槽位，一个物理块 = 16 token × 36 层 = 2.25 MB）。
我们只查 5 层，**所以"5 层全判同"是"36 层全判同"的上界，真实可去重量只会更少**。

宸逸决定不做 36 层对照实验，该偏差只做记录。

V 不经过 RoPE，按理不该对位置敏感。**暂无解释。**
