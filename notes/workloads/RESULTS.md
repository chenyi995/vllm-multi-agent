# 第一部分：九类 workload 的定义

每一类都对应一篇论文提出的真实 multi-agent 结构。
**"agent" 在本实验里不是进程也不是模型副本，就是一段系统提示词**（见 README §5）。

| | 拓扑 | 一句话定义 | 论文 | benchmark | 每题调用数 |
|---|---|---|---|---|---|
| **T1** | Sequential / Pipeline | 五个角色排成流水线依次加工，后面的人看得到前面所有产出 | MetaGPT (ICLR'24) | HumanEval | 5–11 |
| **T2** | Supervisor / Worker | 主管拆子任务 → 工人并行做 → 主管汇总 | AutoGen (2023) | GAIA | 6 |
| **T3** | Fan-out / MoA | 6 个 agent 同时答同一问题，3 层后由聚合者合成 | Mixture-of-Agents (2024) | AlpacaEval 2.0 | 19 |
| **T4** | Debate | 3 个 agent 各自作答，再看别人的答案重答 | Du et al. (ICML'24) | GSM8K | 6 |
| **T5** | Group Chat | 共享群聊记录，主持人每轮用一次调用决定谁发言 | AutoGen GroupChat | MATH level-5 | 24 |
| **T6** | Handoff / Swarm | 客服转接，历史不裁剪、只换身份说明 | OpenAI Swarm | τ-bench airline | 11–13 |
| **T7** | Reflection | 生成 → 评测（真跑测试）→ 自我反思 → 重新生成 | Reflexion (NeurIPS'23) | HumanEval | 4–5 |
| **T8** | Role-play | 两个角色扮演式对话，一个只提问一个只解答 | CAMEL (NeurIPS'23) | AI Society | 20–40 |
| **T9** | Tree Search | 树搜索：展开候选 + 逐个打分 + 保留最好的 5 个 | Tree of Thoughts | Game of 24 | 12–21 |

# 第二部分：实测结果

## 2.1 各拓扑的规模（block 档 16，充足档）

先把四个量定义清楚：

| 量 | 怎么算 | 含义 |
|---|---|---|
| **调用数** | `calls.jsonl` 行数 | 一组配置里 LLM 被调用的总次数 = 10 道题 × 每题调用数 |
| **单 workflow 工作集** | 该 workflow 内**不重复的 block hash** × block_size，10 道题取平均 | 跑完**一道题**缓存里存进过多少 token 的 KV。**决定显存够不够** |
| **N_total** | 该组配置存过的**不重复物理块**总数 | 去重计数的分母 |
| **前缀命中率** | `Σ num_cached_tokens / Σ prompt token 数` | prompt 里有多少比例的 token 引擎发现缓存已有、直接跳过 |


| 拓扑 | 调用数 | 单 workflow 工作集 | N_total（存过的块） | 前缀命中率 | 耗时 |
|---|---|---|---|---|---|
| T1 | 86 | 8,715 | 5,459 | 52.6% | 11 min |
| T2 | 60 | 2,056 | 1,285 | 52.5% | 5 min |
| **T3** | 190 | **78,208** | **48,789** | **1.3%** | 66 min |
| T4 | 60 | 2,155 | 1,347 | 62.9% | 7 min |
| T5 | 240 | 16,300 | 10,188 | **82.1%** | 18 min |
| T6 | 110 | 1,712 | 1,070 | 76.2% | 2 min |
| T7 | 44 | 3,921 | 2,452 | 15.9% | 6 min |
| T8 | 201 | 16,644 | 10,403 | **91.8%** | 27 min |
| T9 | 12 | 1,398 | 874 | 6.3% | 5 min |

**命中率跨了两个数量级**（T3 的 1.3% ↔ T8 的 91.8%），这是九类拓扑最直观的差别：

- **T8 / T5 / T6 命中率高**：两个 agent 轮流说话，各自的输入是"自己的 SYS + 单调增长的同一份历史"，前缀能一直命中。
- **T3 命中率几乎为零**：6 个 proposer 的 persona 各不相同且排在最前面，**从第 0 个 token 就分叉**。

## 2.2 Q2：block 大小的影响

**"有内容孪生的块"占 N_total 的比例**（即理论去重天花板）：

> ⚠️ **这个量与"层"无关。** 判定只看 token id：
> ```python
> groups[tuple(token_ids)].append(block_index)   # 纯文本比对，不碰任何张量
> ```
> 两个块的 token 序列逐个 id 完全相同就算孪生。**36 层共用这一个数**。
> 层的差异出现在**下一步**——逐层用 cosine ≥ τ 判定这些候选里实际有多少真的相同。

| 拓扑 | b16 | b32 | b64 |
|---|---|---|---|
| T3 | **72.7%** | 65.4% | 62.9% |
| T1 | 52.6% | 26.4% | 11.6% |
| T4 | 44.4% | 35.5% | 23.3% |
| T7 | 35.6% | — | 25.2% |
| T6 | 29.0% | 21.9% | 10.3% |
| T9 | 15.4% | 12.8% | 9.2% |
| T8 | 11.9% | 8.1% | 4.5% |
| T5 | 8.3% | 3.1% | 1.6% |
| T2 | 5.8% | 3.7% | 0.0% |

> **规律：block 越大，能匹配上的块越少，且**单调**。**
> 直觉上也对——要求 64 个 token 全部一字不差，比 16 个难得多。
> T1 从 52.6% 掉到 11.6%（**降 4.5 倍**），T2 在 b64 直接归零。
>
> **唯一的例外是 T3**（72.7% → 62.9%，只降 13%）。因为 T3 的重复来自
> "整份 reference 被复制到六个 proposer 的输入里"——**重复的是几千 token 的长段**，
> 不是零星几个块，所以放大 block 也切不断。

⚠️ **4/8 档没有这一行数据**：这两档不 dump 张量（它们的物理块就是 16 token，
与 16 档是同一批数据），按计划 §6.1 要在分析侧按 4/8-token 单元切分复用，
**这段代码还没写**。4/8 档目前只有事件层面的指标（N_total、W、命中率），
实测与 16 档基本一致。

### 三条读得出来的结论

**① 第 0 层，de-RoPE 把候选全部解锁——九类无一例外。**

每一类的 `K_derope` 在 L0 都等于候选总数。因为第 0 层的 K 只取决于
"这是哪个词 + 它在第几位"，把位置拿掉就只剩"这是哪个词"。

**② 增益的大小完全由"内容是否恰好落在同一位置"决定：**

| 增益倍数（L0，K_post → K_derope） | 拓扑 | 为什么 |
|---|---|---|
| **14.2×** | T1 | 同一段函数签名在五个角色的输入里位置各不相同 |
| **6.2×** | T8 | 两个角色的 SYS 长度不同，同一份对话整体平移 |
| **5.9×** | T5 | 同一份群聊记录出现在 manager / Solver / Checker 三种 SYS 之后 |
| 2.6× | T6 | 顾客侧 1,478 字符 vs 客服侧 562 字符，历史平移 |
| 1.7× | T2 | worker 的共享前缀已被运行时合并，剩下的不多 |
| 1.4× | T7 | 迭代之间结构对齐 |
| 1.2× | T3 | reference 长且对齐，大部分同内容块本来就同位置 |
| 1.1× | T4 | 三个 agent 的对话严格对齐 |
| **1.0×** | T9 | 树搜索的 prompt 是同一模板只换数字，位置天然对齐 |

**③ 越深，增益越小；5 层全判同时增益基本归零。**

`K_derope` 与 `K_post` 在 L8 上几乎处处相等，"5 层全判同"这一列两者也几乎相同。

> **原因：深层的 K 是"看过前面所有 token"之后的产物。两段文字即使一字不差，
> 只要前面的上下文不同，深层的 K 就是真的不同——这不是位置造成的，
> 把旋转转回去也救不回来。**
>
> ## 位置不是唯一的障碍，上下文才是。
>
> 对 KV-PIM 的含义：位置无关存储（存不带旋转的 K、读时再加）能拿到的收益
> **集中在浅层**。"去掉 RoPE 就能全层去重"这个假设，本批数据不支持。

⚠️ 而且真要在硬件上去重两个 block，**36 层必须全都相同**——一次分配横跨全部 36 层
（`block_id=5` 指的是每层张量的第 5 个槽位）。我们只查了 5 层，
**所以"5 层全判同"这一列是"36 层全判同"的上界，真实可去重量只会更少。**

### 一个未解释的异常

`V` 在**第 8 层**普遍塌陷：T4 是 **0**、T3 是 **466**（其余层三万）、T8 是 12。
V 不经过 RoPE，按理不该对位置敏感。这说明**第 8 层的 V 对上下文极度敏感**。
**暂无解释，值得单独查。**

## 2.4 容量受限的代价

> **先澄清一个用词**：下表的"需计算"是指**没命中缓存、必须过一遍模型**的 prompt token。
> **充足档没有驱逐，所以那一列全部是首次计算，不是"重算"。**
> 一个 token 命不中缓存有四种原因：① 它就是新内容（绝大多数）；② 前缀断裂——
> 内容一样但前面的东西不一样；③ workflow 之间清了场，每道题从冷缓存开始；
> ④ 引擎永远留最后一块重算。
>
> **受限档比充足档多出来的部分，才是驱逐造成的真·重算。**

| 拓扑 | 端到端延迟（受限/充足） | 需计算的 token（充足档） | （受限档） | 驱逐导致的多算 |
|---|---|---|---|---|
| **T5** | 1.03× | 17.9% | 36.7% | **+105.9%** |
| T6 | 1.00× | 23.8% | 31.3% | +31.1% |
| T1 | 0.99× | 49.4% | 56.9% | +14.9% |
| T4 | 0.96× | 37.1% | 37.9% | +2.1% |
| T2 | 0.98× | 47.5% | 47.5% | +0.0% |
| T3 | 0.99× | 98.7% | 98.7% | +0.0% |

**端到端延迟几乎不变**（0.96–1.03×），因为解码占主导——两档都是每 token 约 **24 ms**，
驱逐的代价在 prefill，被解码时间淹没。

**真正的代价是驱逐导致的多算量。规律很清楚：越依赖前缀缓存的拓扑，被驱逐伤得越重。**
T5 充足档命中 82.1%，受限档掉一半，重算量翻倍；
T3 本来只有 1.3% 命中，驱逐**什么都拿不走**。

# 第三部分：这批数字的适用边界

1. **τ 是工作值**。逐层 τ 取自单条 prompt × 7 个命中边界的标定，正式跑批后须用真实
   trace 重标。L26 的 τ 是 0.964，比 L0 的 0.99999 松三个数量级。
2. **`max_tokens=1024`**（多数论文原文是 2048 或不限）。压短输出让固定长度的
   系统提示词占比上升，**可能人为抬高重复率**，对 T3 影响最大。
3. **5 层采样是上界**（见 §2.3 末）。
4. **4/8 档缺重复度数据**，离线切分代码未写。
5. **T2/T7 的提示词是自拟的**；T1 虽逐字节对齐但产出格式与真实 MetaGPT 不同
   （自由文本 vs 结构化文档），上下文长度会短一个量级。
6. **T6 的转接靠关键词匹配**，实测触发率低，大部分对话停在 triage。
7. **T4 只跑 2 轮**（原文默认），位置错配的量与轮数强相关，可能低估。
8. **T7 尚缺 b32 两组**，其余八类均已跑满 10 组。
