# T3 · Fan-out / Mixture-of-Agents（并行提议 + 聚合）

> 术语见 [`README.md`](README.md)，本文不重复定义｜代码：`kvpim/workloads/t3_fanout.py`

## 一句话

**六个 agent 同时回答同一个问题，把六份答案交给下一层的六个 agent 再答一遍，
三层之后由一个聚合者合成最终答案。**

---

## 1. 模拟的是什么

来自 **Mixture-of-Agents**（Wang et al., 2024）。原文的结构是
**3 层 × 每层 6 个 proposer + 1 个 aggregator**。

原文用**六个不同的开源模型**当 proposer。我们只有一个模型，所以按计划 §3 的
**单模型适配**：*"Qwen3-4B 以 6 个不同 system prompt 扮演 proposer（与'agent = system
prompt'一致）"*。宸逸拍板选了这个口径（而不是六个 proposer 共用同一 SYS）。

**提示词逐字节对齐**：`_with_references` 与 `ref/MoA/utils.py` 的
`inject_references_to_messages` 在 6 个 proposer + aggregator 共 **7 个用例上逐字节相等**
（`analyze.check_moa_reference`，每组配置自动跑）。注入方式也照原文——
references 追加到 **system 消息末尾**，不是 user 轮。

⚠️ 六个 persona 的文本是我写的（原文是六个模型，没有 persona 可抄）。

## 2. 具体任务

**AlpacaEval 2.0** —— 805 条开放式指令，MoA 原文的主评测集。
按指令长度分层抽 10 条，覆盖全部 5 个子集（helpful_base / koala / oasst /
selfinstruct / vicuna）。

例：*"What are places to visit in Montgomery, Alabama?"*、
*"How many balloons would it take to lift a house like in the movie 'Up'?"*

## 3. 一道题怎么跑

19 次调用 = 3 层 × 6 proposer + 1 aggregator。**真实 trace**：

```
call  角色           输入     输出   缓存命中
 0    proposer_0       37      ...      0     ← layer 0：只有 persona + 问题
 …
 5    proposer_5       37     1024      0
 6    proposer_0     4661      642      0     ← layer 1：塞进了六份 reference
 7    proposer_1     4661     1024      0
 …
18    aggregator      ...      ...      0
```

**输入从 37 暴涨到 4,661**：layer 1 的每个 proposer 都要看到 layer 0 全部六份回答。

**缓存命中几乎全是 0**：六个 proposer 的 persona 各不相同，而 persona 排在最前面，
所以**从第 0 个 token 就分叉**。这是宸逸选 6-SYS 方案时就标出的代价——
也让原来的 sanity #5（"命中率接近理论上界"）失效，改成了 Tier 1 + Tier 2。

## 4. 量出来了什么

`block 档 16、充足档`：

```
调用 190 次   W_mean = 78,208 token   W_max = 103,488   耗时 66.1 分钟
N_total = 48,789 个 block                       ← 九类里最大
候选（有内容孪生）= 35,474 个，占 72.7%          ← 九类里最高
```

| 视角 | L0 | L8 | L17 | L26 | L35 | 5 层全判同 |
|---|---|---|---|---|---|---|
| `K_post` | 30,317 | 27,071 | 30,225 | 30,283 | 30,113 | 26,974 |
| `K_derope` | **35,474** | 27,071 | 30,980 | 32,050 | 30,850 | 26,978 |
| `V` | **35,474** | **466** | 30,378 | 30,808 | 25,819 | 466 |

**T3 是重复度最高的拓扑（72.7% 的块有内容孪生）**，原因很直接：
同样的六份 reference，要出现在**下一层六个 proposer 的输入里**，
每份都因为前面 persona 长度不同而落在不同位置。**六份 × 六个位置 = 大量同内容异位块。**

**一个反常的数字**：`V` 在第 8 层只有 **466**，而在第 0 层是 35,474、第 17 层是 30,378。
V 不带位置，按理不该有这种塌陷。这说明**第 8 层的 V 对上下文极度敏感**，
同内容不同前缀的块在那一层差异很大。这个现象在 T4/T5/T6 也出现（T4 第 8 层 V = 0），
**值得单独查一次**，我暂时没有解释。

## 6. 适用边界

1. **六个 persona 是我写的**。原文是六个不同的模型，这是计划授权的单模型适配，
   宸逸拍板。代价是前缀共享几乎完全失效（命中率 6.6%）。
2. **`max_tokens=1024`（原文 2048）**。这条对 T3 影响最大——reference 变短，
   而固定长度的 persona + Aggregate-and-Synthesize 提示词占比上升，
   **可能人为抬高重复率**。T3 的 72.7% 要打这个折扣看。
3. 计划提到可用 **MoA-Lite（2 层）** 压工作集，我们没用，跑的是原文的 3 层。
4. 第 8 层 V 塌陷到 466 这件事没有解释。
