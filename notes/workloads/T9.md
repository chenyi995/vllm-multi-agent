# T9 · Tree Search（树搜索）

> 术语见 [`README.md`](README.md)，本文不重复定义｜代码：`kvpim/workloads/t9_tree_search.py`

## 一句话

**给四个数，凑出 24。每一步让模型列出所有可能的下一步，再给每个候选打分，
留下最好的五个继续往下搜——搜三层。**

---

## 1. 模拟的是什么

来自 **Tree of Thoughts**（Yao et al., NeurIPS'23）。两种调用交替：

```
propose（expander）   给定当前剩下的数字，列出所有可能的下一步算式
value （evaluator）   给定剩下的数字，判 sure / likely / impossible
```

**广度优先搜索，深度 3、宽度 5**：每层把所有存活状态各展开一次，
给展开出来的候选逐个打分，按分数排序留前 5 个进入下一层。

**两段提示词逐字节取自 `ref/tree-of-thought-llm/src/tot/prompts/game24.py`**
（`propose_prompt` / `value_prompt`），`analyze.check_tot_reference` 每组配置自动校验。

**与原文的一处偏离**：原文在 `temperature=0.7` 下对 value 采样三次投票；
本实验锁 `temperature=0`，三次采样必然相同，所以只取一次（计划 §3）。

## 2. 这两段提示词不能套聊天模板

**这是 T9 实现上最关键的一件事，也是它被推倒重跑一次的原因。**

ToT 的提示词是**纯 few-shot 补全**——没有任何指令，就是几个做好的例子，
最后接一句 `Input: 6 7 8 9\nPossible next steps:\n` 等模型往下续：

```
Input: 2 8 8 14
Possible next steps:
2 + 8 = 10 (left: 8 10 14)
8 / 2 = 4 (left: 4 8 14)
...
Input: 6 7 8 9          ← 我们的题
Possible next steps:
                        ← 模型应该从这里开始续算式
```

**套上聊天模板，instruct 模型会把它当成一个问题来回答**，而不是续写这个格式：

> *"Let's analyze the input: 6 7 8 9. We are asked for possible next steps — this likely means…"*

解析器 `parse_candidates` 找不到任何 `(left: ...)`，返回空列表 → BFS 第一层就没有候选
→ **搜索停在根节点**。坏掉的那一版每道题只有 **12 次调用**（现在是 95 上下）。

所以 T9 的调用走 `meta={"raw_completion": True}`，**绕过聊天模板直接发原文**，
这也正是论文当年的用法。同时必须给 stop 序列，否则模型答完会**自己编下一个例子**接着写。

> **这个坏法不会报错。** 引擎正常返回、事件流完整、sanity #4 对账通过，
> 只是搜索树是空的。它是被 Tier 2 的 `output_parseable` 判据抓出来的——
> 而那条判据当初也是补写的，见 [`analyze.md`](analyze.md)。

## 3. 为什么这个拓扑在矩阵里

**它是九类里"同一段长前缀被反复重发、只有末尾几个 token 在变"的极端形态。**

```
propose 的输入 = [固定的 8 行示例（约 150 token）][当前数字]
                  ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 每次 propose 都一样

value  的输入 = [固定的 8 组示例（约 400 token）][当前数字]
                 ^^^^^^^^^^^^^^^^^^^^^^^^^^^^^ 每次 value 都一样
```

**变的只有最后几个 token。** 这让 T9 的前缀命中率 **94.6%，九类最高**
（第二是 T8 的 91.8%，最低是 T3 的 1.3%）。
也让"内容相同但落在不同位置"的块几乎不存在于示例段——示例段永远在开头。
真正的分叉发生在示例之后那一小截数字上。

> **注意 BFS 不回溯。** 每一层结束时 frontier 被整体替换成分数最高的 5 个新状态
> （ToT 自己的 `bfs.py` 也是 `ys = new_ys`），**不会回头激活上一层被淘汰的分支**。
> 所以 T9 考验的是"长前缀反复命中"，不是"旧块被重新用上"。

## 5. 一道题怎么跑

**真实 trace（`T9_w00`，题目 6 7 8 9）**：

```
call  角色         阶段      层   输入   输出   命中   当前数字
  0   expander    propose    0    184    158     0    6 7 8 9
  1   evaluator   value      0    415    128     0    8 9 13     ← 6+7=13
  2   evaluator   value      0    415    128   400    8 9 42
  3   evaluator   value      0    415    128   400    -1 8 9
  4   evaluator   value      0    418    128   400    0.857 8 9
  5   evaluator   value      0    414    128   400    1 8 9
  6   evaluator   value      0    414    128   400    6 7 -1
  7   evaluator   value      0    418    128   400    6 7 0.888
  8   evaluator   value      0    414    128   400    6 9 1
  9   expander    propose    1    183    216   160    8 9 13     ← 进入第 1 层
 10   evaluator   value      1    416    128   400    9 13 17
 ...
本题共 99 次调用
```

**三个可以直接读出来的现象**：

**① 一个 propose 带出最多 8 个 value。** `MAX_CANDIDATES = 8` —— 模型一次列出的
候选取前 8 个。所以每层的调用数 ≈ 存活状态数 × (1 + 候选数)。

**② call 2 起 value 全部命中 400。** value 提示词的固定示例段约 400 token，
**从第二次 value 调用开始就一直命中**，此后每次只需算最后十几个 token。

**③ call 9 的 propose 命中 160。** propose 的示例段约 150 token，同理。

**整棵树的展开（`b16` 档，10 道题合计）**：

```
层   propose   value
 0        10      80     ← 每题 1 次 propose，带出最多 8 个候选
 1        50     400     ← 每题 5 个存活状态各展开一次
 2        50     375
        ----    ----
         110     855     共 965 次调用
```

每题调用数 `[92, 92, 95, 96, 97, 97, 99, 99, 99, 99]`——**很稳**，
因为宽度固定为 5、每次 propose 的候选数几乎都撞上 8 的上限。

| `K_post` | 2,842 | 1,559 | 2,200 | 2,340 | 2,186 | 1,557 |

| 拓扑 | 候选 | L0 `K_post`→`K_derope` | de-RoPE 增益 | L35/L0 保留 | 全层严格/候选 |
|---|---|---|---|---|---|
| T1 | 2,872 | 202 → 2,872 | **14.22×** | 14% | 7% |
| T2 | 75 | 44 → 75 | 1.70× | 59% | 53% |
| T3 | 35,474 | 30,317 → 35,474 | 1.17× | **87%** | **76%** |

| T5 | 848 | 144 → 848 | 5.89× | 32% | 14% |

| T8 | 1,241 | 200 → 1,241 | 6.21× | 40% | 10% |
| **T9** | **3,327** | **2,842 → 3,327** | **1.17×** | **71%** | **47%** |

**① de-RoPE 增益 1.17×，和 T3 并列倒数第二**（最小的是 T4 的 1.13×，但那个数
[有别的原因](T4.md#51-三个辩论者没有在辩论)）。
原因见 §3：示例段永远在提示词最开头，**同内容本来就同位置**，
post-RoPE 已经配上了 2,842/3,327 = 85%。真正错位的只有示例段之后那一小截数字。

**② 深层保留 71%，排第三**（T3 的 87% 最高，T4 同为 71%）。
同样是因为示例段前面没有任何会变的上下文，所以深层的 K 也几乎不变。

**③ 5 层全判同 1,557，占候选的 47%，排第二**（T3 的 76% 最高）。

三条合起来说明：**T9 的重复是"结构性的、稳定的重复"**——
靠的是固定示例段被反复重发，而不是靠 de-RoPE 抢救回来的边缘重复。
这一点与 T1/T8 那种"de-RoPE 增益十几倍、但深层几乎全塌"的形态正好相反。

## 7. 搜索本身跑成了什么样

**value 的判定分布**（855 次）：

```
sure         86
likely      250
impossible  519
```

**36 次没有吐出任何判定词**，按 ToT 自己的 `value_outputs_unwrap` 口径记 0 分。
这条被 Tier 2 记为 `note_value_no_verdict`，**记录但不判失败**——原文就是这么处理的。

**一个必须知道的数字：855 次 value 调用里有 854 次跑满了 128 token 的上限。**
模型吐完判定词之后会继续自己编新的例子往下写。`score_value` 取**第一条独立的判定行**，
所以后面那些编出来的例子不影响打分，但它解释了 T9 为什么比预想慢一倍。

**第 2 层的 375 个候选里，只有 4 个真的剩下一个数且等于 24。** 也就是说这 10 道题
在深度 3 的 BFS 里基本没解出来。**这不影响 KV 的测量**——我们要的是调用的图结构和
前缀共享形态，不是解题正确率——但它意味着 T9 的 trace 是"搜索失败"的 trace，
与 ToT 原文用 GPT-4 跑出的成功搜索形态未必一致。

## 8. 怎么复现

```bash
cd /home/cw636/chenyi/KVPIM/scratch
sbatch -p athena-mini -w node1 --job-name=R9-b16 \
  --export=ALL,BLOCK_TIER=16,TOPOLOGIES=T9,ZMQ_PORT=6511,NUM_TASKS=10,CONFIG_TIMEOUT=7200 \
  run_group.sbatch
```

**两个坑**（都踩过）：

1. **`CONFIG_TIMEOUT` 不能用默认的 3600。** 修好之后每档约 965 次调用、
   充足档实测 54–59 分钟，正好卡在一小时的看门狗上，b4/b16/b32 三档因此被杀过一次。
   现在设 7200。
2. **并行排作业时 `ZMQ_PORT` 至少隔 2。** 每个作业绑两个端口
   （事件 + 补序号缺口的 replay socket），只隔 1 会撞。

## 9. 适用边界

1. **value 只采样一次**，不是原文的三次投票（`temperature=0` 下三次相同）。
   投票能平滑掉单次判定的噪声，少了它，排序更容易被一次误判带偏。
2. **搜索基本没解出题**（§7）：第 2 层 375 个候选里只有 4 个到 24。
   trace 是搜索失败的形态。
3. **`MAX_CANDIDATES = 8` 和 stop 序列都是我加的，原文两样都没有。**
   ToT 的 `get_proposals` 是 `gpt(propose_prompt, n=1, stop=None)[0].split('\n')`
   ——不设 stop、不截断。加上限是为了让每层的调用数可控，代价是模型列出超过 8 个
   候选时后面的被丢掉；加 stop 是因为补全模型答完会自己编下一个 `Input:` 块接着写。
4. **`raw_completion` 让 T9 成为九类里唯一不走聊天模板的拓扑**（§2）。
   它的块内容里没有 `<|im_start|>` 一类的模板 token，与其它八类不可直接比较绝对块数。
5. τ 是工作值；`max_tokens=1024` 的混淆见 [`README.md`](README.md)——
   但 T9 的两种调用各自另有更小的上限（propose 256 / value 128）。
