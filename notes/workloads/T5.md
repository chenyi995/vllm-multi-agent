# T5 · Group Chat（群聊）

> 术语见 [`README.md`](README.md)，本文不重复定义｜代码：`kvpim/workloads/t5_groupchat.py`

## 一句话

**三个 agent 共享一份群聊记录，每一轮由一个"主持人"先用一次模型调用决定谁发言，
被点名的人再发言。**

---

## 1. 模拟的是什么

来自 **AutoGen 的动态 GroupChat**（Wu et al., 2023）。三个 agent
（User_proxy / Solver / Checker）+ 一个 manager，`max_round=12`。

**关键结构**：manager 选人**本身就是一次模型调用**，计入 trace。计划 §3 明确写了：

> *"每轮先由 manager 用一次 LLM 调用（role-play prompt）选 speaker，
> 消息 broadcast 全员共享增长历史"*

**提示词逐字节取自 AutoGen v0.2.34** 的 `autogen/agentchat/groupchat.py`：

```python
select_speaker_message_template = """You are in a role play game. The following roles are available:
                {roles}.
                Read the following conversation.
                Then select the next role from {agentlist} to play. Only return the role."""
select_speaker_prompt_template = "Read the above conversation. Then select the next role from {agentlist} to play. Only return the role."
```

⚠️ **`ref/autogen` 克隆的是 0.4 主线，已经没有 `GroupChat` 了**。必须往同一个克隆里
`git fetch --depth 1 origin tag v0.2.34` 才能拿到这两个模板。这是本实验的一个坑。

⚠️ 三个 agent 各自的 system prompt 是我写的（原文的 A5 场景没有给出逐字提示词）。

## 2. 具体任务

**MATH level-5** —— 竞赛数学题里最难的一档，取六个非几何科目

## 3. 一道题怎么跑

**真实 trace（`T5_w00`）**，24 次调用 = 12 轮 × (manager 选人 + 被选者发言)：

```
call  角色          输入   输出   缓存命中
 0    manager        240      2       0     ← 选人，只输出一个角色名
 1    Solver         108    480       0
 2    manager        726      2     192
 3    Checker        597    140       0
 4    manager        872      3     688
 5    User_proxy     745     25       0
 6    manager        904      3     832
 7    User_proxy     777     25     736
      … 共 24 次
```

**三个结构特征**：

**① 一半的调用是 manager 在选人。** 实测 240 次调用里 **manager 占 120 次**
（Solver 29、Checker 28、User_proxy 63）。这不是 bug，是 AutoGen 的设计——
每次发言前都要先问模型"下一个该谁说"。**这个开销在 KV 上是实打实的。**

**② manager 的输入单调增长且命中很高**（192 → 688 → 832）：
它每轮的消息是 `[固定的选人提示词][整个群聊记录][固定的收尾提问]`，
群聊记录只增不改，所以前缀能一直命中。

**③ 发言者的输入几乎不命中。** Solver/Checker/User_proxy 各自的 system prompt
排在最前面，一换人前缀就断。这就是计划 §3 说的
*"共享 transcript，但 SYS 在最前 → 每个 speaker 前缀在 SYS 处分叉"*。

## 4. 量出来了什么

`block 档 16、充足档`：

```
调用 240 次   W_mean = 16,300 token   W_max = 36,320   耗时 17.6 分钟
N_total = 10,188 个 block
候选（有内容孪生）= 848 个，占 8.3%
```

| 视角 | L0 | L8 | L17 | L26 | L35 | 5 层全判同 |
|---|---|---|---|---|---|---|
| `K_post` | 144 | 118 | 134 | 134 | 126 | 118 |
| `K_derope` | **848** | 118 | 323 | 422 | 271 | 118 |
| `V` | **848** | 104 | 199 | 255 | 131 | 104 |

**T5 的 de-RoPE 增益是九类里相对最大的：144 → 848，5.9 倍。**

原因很清楚：群聊记录是**同一份内容**，但它出现在

- manager 的输入里（前面是选人提示词）
- Solver 的输入里（前面是 Solver 的 SYS）
- Checker 的输入里（前面是 Checker 的 SYS）

**三种前缀长度都不同，所以同一段群聊记录落在三个不同的位置。**
post-RoPE 下它们互不相同（144 个能配上），去掉位置后 848 个全部配上。

> **T5 是"位置错配"最纯粹的例子**：内容完全相同、只有前面挂的 SYS 长度不同。
> 计划 §5.3 把 T5 的损失归因于"驱逐 + SYS 前置分叉"，实测支持后半句。

## 6. 适用边界

1. **三个 agent 的 system prompt 是我写的**，原文没给逐字提示词。
   Tier 1 只覆盖了两个选人模板（对 `ref/autogen` 的 v0.2.34 tag 逐字节校验）。
2. **选人靠字符串匹配**（`parse_speaker`：在回复里找哪个角色名先出现，
   找不到就退回第一个）。模型偶尔会输出解释而不是纯角色名，这个兜底是我加的。
3. **计划 §3 提到"SYS 后置"的对照组**（把公共 transcript 前置、SYS 后置，
   能把不可复用的分叉点往后推）。**这个对照没有做**——它正好是 T5 最该做的实验，
   因为 T5 的重复几乎全部来自 SYS 前置造成的位置偏移。
4. τ 是工作值；`max_tokens=1024` 的混淆见 [`README.md`](README.md)。
