# T6 · Handoff / Swarm（客服转接）

> 术语见 [`README.md`](README.md)，本文不重复定义｜代码：`kvpim/workloads/t6_handoff.py`

## 一句话

**一个模拟顾客和一组航司客服 agent 对话，控制权在客服之间转接，
但对话历史从不裁剪——转接只换最前面的那段身份说明。**

---

## 1. 模拟的是什么

来自 **OpenAI Swarm** 的 airline 示例。五个 agent 组成层级：

```
Triage（分诊）
  ├─ Flight Modification（改签总口）
  │    ├─ Flight Cancel（退票）
  │    └─ Flight Change（改期）
  └─ Lost Baggage（行李丢失）
```

**Swarm 的关键语义**（计划 §3 引 README 原文）：

> *"handoff 不裁剪历史，只换 system prompt"*

也就是说，转接发生时**整段对话原样保留**，只是最前面的 system prompt 从
Triage 的换成 Flight Cancel 的。而这两段长度差很多：

```
triage               562 字符
flight_modification  606
flight_cancel      1,895     ← STARTER_PROMPT + 退票政策
flight_change      1,893
lost_baggage       1,581
```

> **所以每次转接，整条历史的 token 位置都会平移一大段。**
> 计划 §3 原话：*"SYS 长度不同使整条历史 token 位置平移（de-RoPE 相关）"*。
> **这是 T6 存在于矩阵里的理由。**

## 2. 提示词从哪来

**运行时直接从 `ref/` 读**，不是抄进代码：

```python
_constants(AIRLINE / "data/routines/prompts.py", {"STARTER_PROMPT", "TRIAGE_SYSTEM_PROMPT"})
_constants(AIRLINE / "data/routines/flight_modification/policies.py",
           {"FLIGHT_CANCELLATION_POLICY", "FLIGHT_CHANGE_POLICY"})
```

理由：五个 agent 的提示词加起来约 6 KB，抄进代码等于制造第二份会漂移的副本。
代价是 T6 依赖 `ref/` 存在。

⚠️ 那两个 policy 是 **f-string**，所以 `_constants` 用 `exec` 而不是 AST 取值——
执行前断言过这些文件**没有任何 import**。

**用户模拟器**的提示词逐字取自 `ref/tau-bench/tau_bench/envs/user.py`，
终止标记 `###STOP###`。计划 §3 明确要求：
*"τ-bench 配 LLM user simulator（其调用同样进 KV cache，计入 trace）"*。

## 3. 具体任务

**τ-bench airline 域** —— 50 个客服任务，等距抽 10 个。每个任务给模拟顾客一段
角色设定，例如：

> *"Your user id is mia_li_3668. You want to fly from New York to Seattle on May 20
> (one way). You do not want to fly before 11am est... You are reactive to the agent
> and will not say anything that is not asked."*

## 4. 一次对话怎么跑

**真实 trace（`T6_w00`）**，13 次调用：

```
call  角色              输入   输出   缓存命中
 0    user_simulator     355     29       0
 1    triage             159     19       0
 2    user_simulator     397     26     336     ← 顾客侧命中很高
 3    triage             212     16     176
 4    user_simulator     447     25     416
 5    triage             261     78     224
 6    user_simulator     558     55     464
 7    triage             402     19     336
      … 共 13 次
```

**两个特征**：

**① 两边都是"自己的 SYS + 同一份对话历史"**，各自单调增长，所以**各自内部**命中很高
（顾客侧 336 → 416 → 464，客服侧 176 → 224 → 336）。

**② 顾客和客服看到的是同一段对话，但角色视角互换、SYS 不同** ——
`user_simulator` 的 SYS 是 1,478 字符的任务设定，`triage` 的是 562 字符。
**同一句话在两边落在完全不同的位置。**

**实测转接很少发生**：110 次调用里 `triage` 占 43 次，
`flight_modification` 只有 2 次、`flight_change` 3 次、`lost_baggage` 2 次。
说明模型大多数时候停在分诊没往下转。**这是一个如实的观察**——真实 Swarm 里
转接由 function call 触发，我们没有工具环境，只能从回复文本里认关键词（`next_agent`），
识别率不高。

## 5. 量出来了什么

`block 档 16、充足档`：

```
调用 110 次   W_mean = 1,712 token   W_max = 4,240   耗时 2.3 分钟   ← 九类里最轻
N_total = 1,070 个 block
候选（有内容孪生）= 310 个，占 29.0%
```

| 视角 | L0 | L8 | L17 | L26 | L35 | 5 层全判同 |
|---|---|---|---|---|---|---|
| `K_post` | 117 | 117 | 117 | 117 | 117 | 117 |
| `K_derope` | **310** | 117 | 200 | 222 | 159 | 117 |
| `V` | **310** | 88 | 139 | 158 | 117 | 88 |

**`K_post` 在五层上都是 117，完全平坦** —— 九类里独一份。
这 117 个块是"同内容**且**同位置"的（多半是每轮固定的对话模板），
它们在任何层都相同，所以不随层深变化。

**de-RoPE 在第 0 层把 117 抬到 310（全部候选），2.6 倍。**
多出来的 193 个就是"同内容、异位置"的块——即顾客侧与客服侧看到的同一段对话，
因为 SYS 长度差（1,478 vs 562 字符）而整体平移。

> **T6 直接验证了计划 §3 的预判**：SYS 长度不同导致整条历史平移，
> 这些块 post-RoPE 下配不上、de-RoPE 后能配上。

## 7. 适用边界

1. **转接靠关键词匹配，不是 function call。** 真实 Swarm 用工具调用触发 handoff，
   我们从回复文本里找关键词（`_AGENT_MENTION`）。实测转接触发率低，
   **大部分对话停在 triage**——这削弱了"转接导致位置平移"这一效应的样本量。
2. **没有工具环境**：客服 agent 查不了订单、改不了票，只能对话。
   τ-bench 的正确率完全不适用，我们只用它的对话结构。
3. **提示词运行时从 `ref/` 读**，所以 T6 无法在没有 `ref/` 的环境里跑。
   也因此它没有独立的 Tier 1 校验函数（字符串**就是**参照物）。
4. **`_constants` 用 `exec` 执行 `ref/` 里的文件**（因为 policy 是 f-string）。
   执行前断言了那些文件无 import，但这仍然是在执行第三方代码。
5. τ 是工作值；`max_tokens=1024` 的混淆见 [`README.md`](README.md)。
